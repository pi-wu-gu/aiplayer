# dig 与 look_lock 实现方法分析（v0.2.1.35）

> 需求原文：「添加破坏指定方块的工具（开始破坏方块，检测并等待破坏完成，超时未完成报错给模型），
> 视角朝向锁定至指定方块工具（限制最大持续时间，任何视角操作都会中断其锁定），分析实现方法」
>
> 结论先行：两个工具各新增一个一等动作（`dig` + `dig_status`、`look_lock`），
> 核心范式是「**主线程只发起、tick 钩子推进、终态墓碑可查**」的长时程动作三段式。
> 2026-10-17 部署 0.2.1.35 后实网验证全部通过。

---

## 1. 需求拆解与关键约束

### 1.1 两个工具的真实语义

| 工具 | 用户要求 | 隐含语义 |
|---|---|---|
| 破坏方块 | 开始破坏、**检测并等待**完成、超时报错给模型 | 跨 tick 长任务 + 可查询进度 + 明确失败信号 |
| 视角锁定 | 锁定至指定方块、**限制最大持续时间**、任何视角操作中断 | 持续维持 + 有界生命周期 + 被抢占即失效 |

### 1.2 三个硬约束（决定了架构，不是细节）

在写任何代码之前，先摸清了模组现有的三个机制边界——**它们直接排除了最直觉的实现方式**：

| 约束 | 事实 | 排除了什么 |
|---|---|---|
| **主线程动作体不能阻塞** | `ControlServer.runOnClientThread` 用 `mc.execute()` + `CountDownLatch`(20s) 把动作体放到客户端主线程执行。动作体若循环等"方块被挖掉"，主线程被占住 → tick 永不来 → 等不完 → **死锁** | ❌「动作体内 while 循环等破坏完成」 |
| **agent 侧 POST 只等 8 秒** | `mc_bridge.mc_act` POST timeout=8 且不读响应体，靠轮询 `/state.last_action`（20s 截止）判定结果 | ❌「一个 HTTP 请求里同步等 15s 破坏」 |
| **按键注入链路有抓取门禁** | 旧挖矿法 `keys key.attack` 长按 → 原版 `handleKeybinds` 四门禁 `screen==null && !flag2 && keyAttack.isDown() && isMouseGrabbed()`；窗口后台时 `grabMouse()` 静默 no-op → 破坏进度每 tick 被 `stopDestroyBlock()` 清零（2026-10-17 四层证据实锤） | ❌「继续用按键注入模拟挖矿」 |

**这三个约束共同指向同一个架构**：长时程动作必须拆成「发起 / 推进 / 查询」三段，
且推进不能依赖按键链路。模组里已有先例——`sign_edit` 的 pending 模式（异步编辑告示牌），
新工具复用同一范式，只是推进逻辑不同。

## 2. 架构：长时程动作三段式

```
┌─ 动作体（主线程，立即返回）─────────────────────────────┐
│ dig {x,y,z,timeout_ms}                                  │
│  ① 前置校验（空气/流体/距离 6 格/权限）                  │
│  ② gameMode.startDestroyBlock(pos, dir)  ← 只发起       │
│  ③ 返回 {"result":"dig_started", ...} 立刻返回          │
└─────────────────────────────────────────────────────────┘
                    ↓ 任务对象（DigTask）落静态字段
┌─ ClientTickEvent.Post（每 tick，主线程）────────────────┐
│ tickDig()：                                             │
│  ① 环境复检：死亡/开界面/使用物品/走远 → failDig        │
│  ② 超时判定 → timeoutDig（带 progress_stage + hint）    │
│  ③ continueDestroyBlock + getDestroyStage() 推进        │
│  ④ 连续 3 tick 空气 → breakDig（防服务端驳回误报）      │
└─────────────────────────────────────────────────────────┘
                    ↓ 终态
┌─ 查询与播报──────────────────────────────────────────────┐
│ dig_status → idle / running(进度) / 终态墓碑            │
│ ChatBuffer.add("[dig] ...") → 模型从聊天尾部可见        │
└─────────────────────────────────────────────────────────┘
```

### 2.1 为什么是「静态单任务槽」而不是队列

- 挖矿在语义上天然单线程：同一时刻只该有一个破坏目标
- 并发控制退化成一条规则：**新 dig 自动取消旧 dig**（`被新的 dig 取代`），
  自愈而非报错——daemon 连发指令时不会卡死（实网验证了这个路径）
- 终态保留为「墓碑」（`state=broken/timeout/failed/cancelled` + `terminal` JSON），
  附 `ended_age_ms` 防止模型拿到陈旧结果误判——这是从「agent 拿不到失败信号白烧 87 万 token」
  的事故里学到的：**长任务的失败必须可查询、可辨龄**

### 2.2 look_lock 的「维持 + 中断」双机制

锁定不是设一次朝向就完事——玩家在移动，眼睛与目标的相对方位每 tick 都在变：

```
每 tick：
  ① 到期？           → duration_end（非错误）
  ② 朝向 ≠ 上 tick 写入值（>0.05°）？→ interrupted（外部操作检测）
  ③ 否则：重算眼睛→目标 yaw/pitch，写 yRot/xRot（连带 yRotO/xRotO 防渲染插值抖动）
```

中断检测用 `Mth.wrapDegrees` 做差值（防 359°→1° 的回绕误判）；此外 `look`/`turn`/`mouse_move`
三个动作末尾**显式调用** `cancelLookLock()`——比等下一 tick 的差值检测更即时、原因字符串更明确
（实测输出 `interrupted: 被 look 动作中断`）。真实鼠标移动没有显式入口，靠差值检测兜底。

## 3. 关键实现细节（踩过的坑）

| # | 细节 | 做法与理由 |
|---|---|---|
| 1 | **破坏 API 选型** | `MultiPlayerGameMode.startDestroyBlock(pos, dir)` + 逐 tick `continueDestroyBlock(pos, dir)`——与真人鼠标按住同一条服务端路径，创造分支瞬破、生存分支累积 `destroyProgress`；`getDestroyStage()` 公开可读进度 0-9，直接作为 `progress_stage` 暴露给模型 |
| 2 | **打击面方向** | `Direction.getNearest(-dx,-dy,-dz)`（从方块指向玩家的反方向）= 准星命中时的 face 语义，服务端校验同源 |
| 3 | **完成判定防误报** | 客户端破块是**先斩后奏**（预测发包），服务端可能驳回 → 回滚成原方块。单 tick 看到空气就报成功会撒谎 → **连续 3 tick 空气**才算 `dig_broken` |
| 4 | **超时报错的诊断价值** | timeout 不是简单一句"失败了"：附 `progress_stage` + `gamemode` + hint——stage=0 且耗时远低于徒手工时 → 工具不对（先 `select`）或不可破坏（基岩/硬度-1）；stage 有累积没到顶 → 加大 timeout。**让模型能自己定位原因，而不是盲目重试** |
| 5 | **每 tick 环境复检** | 玩家死亡 / 界面打开（`mc.screen != null`）/ 使用物品中 / 走出 6 格 → 立即 `failDig` 带具体原因。长任务最大的风险是"悄悄烂掉"，复检让每个失败都有名字 |
| 6 | **权限轴归属** | dig 属"改世界"类 → 入 GATED 集合，`gameActionMode=safe` 起缺席（与 press/keys 同轴，装配期摘除）；`dig_status` 只读 → 常驻；`look_lock` 纯视角 → 与 look/turn 同待遇不过轴。**闸门在装配期，改 toml 无需重启** |
| 7 | **参数夹取** | `timeout_ms` clamp [500, 25000] 默认 15000；`duration_ms` clamp [200, 60000] 默认 5000——上限防"永久锁定挡住其他操作"，下限防"发起即超时"的无意义任务 |
| 8 | **坐标语义对齐 look** | 整数坐标 → 瞄方块中心（+0.5）；小数坐标 → 瞄原点点。与既有 `look` 动作完全一致，模型零学习成本 |
| 9 | **编译期两个坑** | ① `BlockState` 在 `net.minecraft.world.level.block.**state**.BlockState`（不在 `.block` 包）；② `Json.num` 只有 `double`/`long` 重载，三元表达式混 `String` 编译不过 → 拆开写 |

## 4. agent 侧同步（工具描述即接口）

模组加动作只是半个交付——**模型不知道有这些动作就等于不存在**。同步了三处：

1. **`mc_bridge.py` keep 列表**：`mc_state` 新增 `window_active` / `mouse_grabbed` 诊断字段
2. **`mc_act` 工具描述**：新增「挖掘」组（dig 异步 + 轮询纪律 + dig_status）、视角组补 look_lock；
   **修正旧文案**「★模组没有 place/dig/…挖方块=look+keys key.attack」——这句已经害死了砍树任务
3. **`PRIMARY_PROMPT`**：【挖方块】整段重写（异步轮询纪律 + 旧法废弃警告 + 超时 hint 解读）；
   新增【视角锁定】段；移动失效排查段补窗口诊断字段

另更新 `README.md`（新章节 + 动作表）、`docs/动作备忘.md`（挖矿/锁定两节 + 动作总数）、
`docs/记忆/2026-10-17-挖方块诊断.md`（追加"已修复"章节，记录修复方向 1 为何未采纳）。

## 5. 实网验证结果（0.2.1.35 部署后）

验证环境刻意选在最恶劣条件下：**游戏窗口在后台（`window_active=false`）+ 鼠标未抓取
（`mouse_grabbed=false`）**——这正是旧法挖矿 100% 失败的环境。

| 验证项 | 命令 | 结果 |
|---|---|---|
| 动作注册 | `/actions` | ✅ 「挖掘」组 dig/dig_status、「视角」组 look_lock 在位；54 实现 / 92 名 |
| **窗口后台挖矿** | `dig` (-2,65,3) dirt | ✅ **`dig_broken` 用时 0.8s**（旧法此环境零进度）；`block_at` 复核已变空气 |
| daemon 自动采用 | 定时唤醒任务 | ✅ 醒来即用 dig 砍树：dark_oak_log ×4（3.0-3.3s/个）、grass_block 1.1s，工时全部符合生存徒手标准 |
| 状态查询 | `dig_status` | ✅ 终态墓碑带 `ended_age_ms`；聊天播报 `[dig] 已破坏 … 用时 0.8s` |
| 单任务槽自愈 | daemon 连发 dig | ✅ 旧任务 `dig_cancelled: 被新的 dig 取代`，新任务正常完成 |
| **超时报错** | `dig` timeout_ms=500 | ✅ `dig_timeout` 附 `progress_stage:5` + `gamemode` + 完整 hint（实测 527ms 截止） |
| 距离前置校验 | `dig` 12 格外石头 | ✅ `dig_err: 目标超出破坏距离（13.1 > 6.0 格）`，未发起 |
| 锁定维持 | `look_lock` duration 8000 | ✅ 8 秒无外部操作 → `duration_end` 自然到期 |
| **锁定中断** | `look_lock` 后发 `look` | ✅ `interrupted: 被 look 动作中断`（显式取消路径，1.7s 时触发） |
| 诊断字段 | `/state` | ✅ `window_active:false` / `mouse_grabbed:false` 正确反映后台状态 |

## 6. 设计取舍记录

| 决策 | 选择 | 放弃的方案与理由 |
|---|---|---|
| 挖矿实现路径 | gameMode API 一等动作 | 输入层强制抓取鼠标（`grabMouse` 反射 + `isWindowActive` 绕过）——会改全局输入状态（`KeyMapping.setAll()` 擦合成 isDown、`missTime=10000` 副作用），且治标不治本 |
| 长任务模型 | 三段式异步 + 墓碑 | 动作体内同步等待——主线程死锁（约束 1）；POST 长轮询——agent 侧 8s 超时（约束 2） |
| 并发语义 | 单槽 + 新任务取代旧任务 | 任务队列——挖矿无并发需求，队列只会增加状态机复杂度 |
| 完成判定 | 连续 3 tick 空气 | 单 tick 空气——服务端驳回会回滚，误报成功比晚报成功更糟 |
| 锁定中断检测 | 显式取消 + 差值检测双路 | 仅差值检测——look/turn/mouse_move 有明确入口，显式取消原因字符串更可读 |

## 7. 遗留事项

- **合成配方辅助**仍未解（目前只有切石机 `cont_button` 一条路，无通用"按配方合成"）——与本次需求无关，记录备查
- `look_lock` 与 `dig` 可以组合（锁定时挖矿不冲突，dig 不依赖视角），但未做组合场景的专门验证——语义上正交，风险低
- `missTime` 诊断字段未加（修复方向 3 的第三项）：dig 已绕开门禁，按键类问题用前两个字段已足够，不加是为避免 state 膨胀
