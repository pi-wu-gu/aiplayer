# TLM FastPack（mixin patch）兼容性影响分析

> 2026-10-18 · 针对「跳过 TLM 默认包重复解压」方案 A 的决策评估
> 前置事实见《2026-10-18-启动与运行缓慢-根因分析.md》：解压本身 0.96s/1260 文件，
> 慢在 FML UnionFileSystem 逐文件元数据操作，三次实测 471-1113s。

## 一、Patch 的确切行为（分析基准）

独立小 mod（modId 建议 `tlm_fastpack`，约 100 行），只含一个 mixin，不动 TLM 原文件：

```
注入点  GetJarResources.copyFolder(String resource, Path target)  @HEAD, cancellable
跳过条件（全部满足才 cancel）：
  ① target 目录存在且文件数 ≥ 1000
  ② marker 文件记录的 TLM mod 版本 == 当前 TLM mod 版本
  ③ jar 内默认包条目数 == 磁盘文件数，且未压缩总大小一致（读 zip 中央目录，毫秒级，不解压）
不满足 → 放行原逻辑（首次启动 / TLM 升级 / 目录损坏时自然回退全拷）
```

## 二、兼容性影响矩阵

| 维度 | 影响 | 依据 / 防护 |
|---|---|---|
| **TLM 常规升级** | ✅ 无损 | marker 记录 TLM mod 版本（`1.5.3-neoforge+mc1.21.1`），升级后版本不等 → 自动全拷一次，之后恢复快启 |
| **TLM 重构 copyFolder**（改名/改签名） | ⚠️ 唯一真实风险点 | mixin 用 **`expect` 而非 `require`**：注入失败只打 WARN，patch mod 静默让路，TLM 回到慢路径（15 分钟），**不会崩游戏**。另加 mixin plugin `shouldApplyMixin` 预检目标类是否可加载，TLM 不在场时完全不挂载 |
| **NeoForge / MC 版本升级** | ✅ 低 | 目标是 **mod 自己的类**（非 MC 混淆类），**不需要 refmap**，混淆映射变化与它无关；mixin mod 只需跟着整合包重编译（一般不用改代码） |
| **与其他 mod 冲突** | ✅ 极低 | 冲突仅当别人也注入同一方法——`GetJarResources` 在 TLM 内**只有一个调用方**（`CommonDefaultPack`，字节码实证），生态内无已知竞争者；TLM 自身本就有 25 个 mixin，再加一个是常态 |
| **`tlm_custom_pack` 里的用户自改内容** | ⚠️ **行为语义变化（正向）** | 现状：每次启动上游**覆盖**用户对该目录的修改；patch 后：用户编辑**得以保留**。若有人依赖"启动自动重置"，语义变了——但该目录本就是 TLM 给用户的自定义包工作区，覆盖用户编辑更像上游 bug。要在 patch 文档里显式声明 |
| **服务端** | ✅ 无影响 | `copyFolder` 只有 `CommonDefaultPack` 调用；`ServerCustomPackLoader` / `CustomPackLoader` 只**读**该目录不解压（引用面实证）。patch 不改变它们看到的内容 |
| **目录损坏 / 用户误删部分文件** | ✅ 自愈 | 条件①③不满足 → 自动全拷，无需人工干预 |
| **marker 文件损坏 / 被删** | ✅ 自愈 | 视为"未跳过"→ 全拷一次并重写 marker |
| **TLM 被移除后** | ✅ 空转 | mixin plugin 检测不到目标类 → 不挂载；mod 常驻但零开销。也可直接删掉 patch mod |
| **TLM 同版本号改包内容**（罕见） | ⚠️ 有兜底 | 条件③的**总大小校验**能抓住绝大多数内容变更（条目数和字节数同时不变才算漏网——概率极低）；这是"每次全拷"与"完全不校验"之间的折中 |
| **安全/签名** | ✅ 无 | mod jar 不签名；patch mod 是独立 jar，不触碰 TLM 字节码文件本身 |
| **性能** | ✅ 正收益 | 每次启动省 8-19 分钟；patch 自身开销 = 一次目录 count + 读 zip 中央目录（<50ms） |

## 三、失败模式与降级路径汇总

```
mixin 注入失败（TLM 重构）      → expect → WARN 一条 → TLM 慢路径（15min），游戏正常跑
TLM 升级                       → marker 版本不等 → 全拷一次（预期内），之后恢复 <1s
TLM 同版本改内容               → 条数/字节数校验 → 大多数情况重拷；极小概率漏更（可接受）
目标目录删一半                 → 条数检查 → 全拷自愈
patch mod 自身出错抛异常       → mixin HEAD cancel 抛异常会传导 → 包 try-catch，出错时放行原逻辑
```

**最坏情况 = 回到今天的现状**（15 分钟慢启动），没有任何场景比现状更糟。

## 四、顺带：`glDebugVerbosity:0` 的兼容性

- **原版官方选项**（Options 序列化字段，反编译实证），非 hack；
- `0` = 不安装 KHR_debug 回调，**零运行开销**，完全可逆（删掉那行即恢复默认 1）；
- 无任何 mod 依赖该日志输出（它是诊断信息）；唯一代价：排查渲染问题时排查信息变少——
  临时把值改回 1 即可，比坏纹理每帧刷 489MB 日志的代价小几个量级。

## 五、结论

| | mixin patch | 禁用 TLM | 维持现状 |
|---|---|---|---|
| 启动收益 | **8-19 min → <1s** | 15 min → 0 | — |
| 兼容性风险 | 低（唯一风险点有 expect 兜底，最坏=现状） | 存档女仆失效（不可逆功能损失） | 每次启动 15 分钟 |
| 维护成本 | TLM 大版本重构时可能要跟进一次 | 零 | 零 |

**建议做**：风险被 `expect` + plugin 预检压到"最坏等于现状"，且附带修复了"上游每次启动覆盖用户自定义包"的语义问题。唯一要接受的是 TLM 未来大重构时需要跟进检查一次（届时现象只是"启动又变慢了"，不会坏）。
