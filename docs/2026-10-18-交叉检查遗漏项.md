### A3. ★`file_mode: off` 会被解析成"全开"（权限反转）

`agents/roles.yaml` 里 `planner` 写的是：

```yaml
  file_mode: off
```

PyYAML 按 YAML 1.1 把裸 `off` 解析成**布尔 `False`**，而旧实现：

```python
str(False or "")      # → ""      （False 是假值，or 走到右边）
_ALIASES.get("", ...) # → "full"  （认不出就按最宽松来）
```

于是 `planner` 的 `file_mode` 实际是 **`full`**。同理，机主要是配 `permissions.file_mode: off`
想关掉文件能力，结果变成**全开**——方向完全相反。

已修两处：
- `file_io.normalize_mode()`：显式 `isinstance(value, bool)` → `False→off` / `True→full`
- `file_ops._cfg_mode()`：同样处理（`destructive_file: off` 之前会落回 `approval`，虽方向保守但也是失效）
- `roles.yaml` 里的 `off` 加引号 `"off"`（双保险）
- 新增 3 个测试锁死（`test_permissions.py` 15 → **18 项**）

### B3. `mc_batch` 的 fail-fast 说法是错的

我之前在《框架工具.md》写「中间某步失败不会中断后续（**fail-fast 只发生在权限拒绝**）」。
读 `ControlServer.java` 的 `commands()` 确认：

```java
for (JsonElement el : cmds) {
    ...
    if (r.ok()) ok++; else { failed++; COMMAND_ERRORS.incrementAndGet(); }
    results.add(...);       // ← 没有 break，权限拒绝也不 break
}
```

**任何失败都不中断**，逐条执行到底。另外 `mc_batch` 框架侧拿到的是
"观察到 `last_action` 变化时的结果"，**不保证是最后一个动作**——批里有 `dig`/`place`
这类异步动作时可能拿到中间态。文档已改。

### B4. 角色工具白名单没跟上工具扩容

`auditor` 角色（行为审计）原本只有 `tools: [file_read]`。
现在框架有 `file_grep` / `file_list` / `file_stat`，而审计日志恰恰最需要 grep。
已扩为 `[file_read, file_list, file_grep, file_stat]`，`file_mode: readonly` 仍收窄。

## D 类：流程改进建议

### D1. 加一个启动自检（最能防复发）

今天"配置写了不生效"出现三次：`session_token_budget: 0`、`approval` 段读错层级、
`file_mode: off` 变 full。共同点是**表象正常**，只有专门去验才会发现。

建议启动时打印一张"配置生效值表"，把 yaml 值与代码实际读到的值并排输出，不一致就告警。
实现成本低（各模块已有读取函数），收益是以后这类问题**在启动那一刻就暴露**。

### D2. 加"文档 ↔ 代码"数字校验

动作数（102）、工具数（17+5）、配置键数（70/71）、版本号——这些数字靠人肉同步，
今天一次就找出 6 处漂移。

建议一个 `scripts/check_docs.py`：调用 `{"type":"actions"}`、`build_primary_registry()`、
解析 config、读 `gradle.properties`，与 md 里的断言比对，不一致就列出来。
