## 一、检查方法

四路交叉验证，单路不足为凭：

| 路径 | 做法 | 能发现什么 |
|---|---|---|
| ① 注册表枚举 | 跑 `orchestrator.build_registry(cfg)`，打印工具名/描述/manifest 键 | 装配期问题（条件注册、权限收窄、配置缺失） |
| ② 闭包 fn 实测 | 按真实签名逐个调用（**不传 cfg**，cfg 由闭包捕获），判定返回值 | 运行期问题（签名错配、cfg 加载不全、依赖缺失） |
| ③ 说明文档三源比对 | PRIMARY_PROMPT ↔ mc_act manifest ↔ shared 区 docs 三边互相验证 | 文档漂移（提示词教的、manifest 没写的、agent 查不到的） |
| ④ 在线 /actions 比对 | 部署后比对模组 `/actions` 分组表 vs Java 注册表 | 动作对 agent 自省「隐身」（注册了但分组表没列） |

关键坑（本次实测踩到）：cfg 必须走 `config_loader.full_load()`——裸 `yaml.safe_load` 缺 `_providers`/`_model_prices`，`balance_query` 直接 `KeyError`。工具 fn 签名也易错：`_state(fields=None)` / `_act(type, **kwargs)` / `_batch(actions)` / `_chat(count)` / `_read(path, max_chars)` / `_write(path, content, append)` / `_fetch(url,...)`——闭包已捕获 cfg，**调用不传**。

## 三、发现的问题与修复明细（3 个真问题 + 1 个流程坑）

### 问题 1：`actionsList()` 分组表漏列 5 个已注册动作 → agent 自省「隐身」

- **现象**：Java `Actions.register` 注册了 92 个动作名，但 `actionsList()` 的**硬编码分组表**只列了其中一部分。`connect`（联机）、`be_nbt`/`item_nbt`（NBT 读取）、`sign_edit`/`sign_read`（告示牌）**不在任何组里**——注册表与展示表是两套东西，漏同步 = agent 通过 `/actions` 自省时看不到这些动作。
- **根因**：register 与 actionsList 无一致性校验，纯手工维护。
- **修复**（`Actions.java`）：新增两组 + connect 入通信组：
  ```java
  groups.put("方块实体/物品数据", List.of(
          "be_nbt(nbt_read/block_entity_nbt)：读任意方块实体已同步 NBT（SNBT 截断4000）...",
          "item_nbt(held_nbt/item_components)：读物品完整数据组件（耐久/附魔/自定义名，SNBT）..."));
  groups.put("告示牌", List.of(
          "sign_edit(sign)：写正反面 4 行文本...★写文本只能用这个，禁止逐键 press 打字",
          "sign_read(sign_text)：读正反两面 4 行文本/颜色/辉光标志..."));
  groups.put("通信", List.of("say(chat)", "command(cmd)",
          "connect(join)：高级联机——立即连接 address 或配置地址，并清零自动连接预算"));
  ```
- **验证**：部署 0.2.1.35 后 `/actions` 返回 **16 组**，5 个动作全部在列，新组「方块实体/物品数据」「告示牌」就位。

### 问题 2：mc_act manifest 完全缺失「自建区文件动作」组 → agent 查不到笔记通道

- **现象**：PRIMARY_PROMPT 教 agent 用 `mc_act file_read/file_append` 读写 shared 区文档（物品对照/记忆/自建工具索引），但 `mc_act` 工具的 manifest 里**一个字都没有**——也就是说提示词依赖的能力在工具自描述里不可见，agent 自查 manifest 时会以为没有这条通道。
- **修复**（`tools/builtin/mc_bridge.py`）：
  - 新增「**自建区文件动作**」组：`file_read/file_write/file_append/file_list/tools/docs` + **与 framework `file_*` 工具的分辨规则**（相对路径语义完全不同：mc_act 的相对路径相对 shared 区根，framework 的相对路径相对 agent 根）
  - 视角组补 `look_lock`；新增「挖掘」组（dig 异步 + 轮询纪律 + dig_status）；connect/agent_status/llm_chat 补说明
  - 修正「★模组没有 place/dig」旧文案（dig 已于 0.2.1.35 落地）
- **验证**：sidecar 新版 manifest grep 命中；`mc_act file_append` 写 + `file_read` 回读在线通道实测通过。

### 问题 3：PRIMARY_PROMPT 三处旧指引教 agent 用错文件通道

- **现象**：提示词教 agent 用 **framework `file_*`** 去读写 **shared 区**（游戏目录 `aiplayer/`）文档。但 framework file_* 的相对路径落 **agent 根**——agent 会把「物品对照笔记」写到错误的位置，且 framework 工具白名单根本不含 shared 路径（只能绝对路径），实际调用会失败。
- **涉及三处**：①物品对照读写指引 ②记忆查询指引 ③自建工具 `tools/index.json` 读取指引。
- **修复**（`core/runner.py`）：全部改为 `mc_act file_read/file_append`（相对路径相对 shared 区根）；`_auto_memory_block` 截断提示同步；`FINALIZE_PROMPT` 的落盘路径改 `mc_act file_append path="docs/记忆/last_run_plan.md"`。
- **附带**：新增【文档索引（shared 区）】段，登记 `docs/框架工具.md / 动作备忘.md / 配置说明.md`，agent 醒来即可自查文档地图。

### 问题 4（流程坑）：改 agent 源码只 `gradlew build` 不生效

- **现象**：改了 `runner.py`/`mc_bridge.py` 后构建部署，sidecar 里跑的还是旧代码。
- **根因**：jar 内嵌的是**静态 bundle**（`assets/aiplayer/agent_bundle.zip`），编译不会重新打包它。且部署时 sidecar 已存在同名版本目录，`isDeployed` 版本 marker 匹配 → **跳过解压**。
- **正解（四步链，已写进 README 构建节）**：
  1. `scripts/build_agent_bundle.py` 重打 bundle（本次产物 206 条目 11.3MB，smoke 通过）
  2. `cp` 到模组 `src/main/resources/assets/aiplayer/`
  3. `gradlew build`
  4. 部署时**先删 `aiplayer-agent/<版本>` 目录**再重启（否则 marker 命中不解压）
- **踩坑记录**：删目录时被 daemon 进程占用 → genie-trash fail-closed 报「Some operations were aborted」→ 必须先杀进程树（supervisor→java→daemon）再删。本次连踩两次，均已记入 README + 工作日志。
