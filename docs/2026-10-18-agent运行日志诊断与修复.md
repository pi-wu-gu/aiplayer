## 一、最刺眼的现象

一次**"检查积压未读消息"的定时唤醒**，跑了 **25 轮 / 69.8 秒 / 388,240 token**，
而它实际要做的只有"看一眼聊天、发现没人在喊我、收尾"——3 轮足够（12 万 token 以内）。

`behavior_20261018_031332.log` 里的完整时间线：

| 轮 | 模型在想什么 | 后果 |
|---|---|---|
| 1-3 | 查状态、查时间、统计 → 输出"本次唤醒处理完毕，无待办" | 框架判定"没说完" |
| 4 | 无工具调用，纯结论 | **被注入"任务尚未完成，继续执行剩余步骤"** |
| 5-14 | 被迫再查一遍聊天/状态/在线名单/日档 | 重复劳动 |
| 15 | 又给结论"确认完成，无剩余可执行事项" | **又被注入"继续"**（第 2 次） |
| 16-21 | "The user says task not complete…" → 再查聊天、状态、日档 | 开始用英文思考（上下文错乱） |
| 22 | 再给结论 | **第 3 次注入"继续"** |

同期其它运行同样膨胀：`02:48 mention → 176.4s / 25 轮`、`02:50 mention → 144.9s / 26 轮`、
`02:53 scheduled → 124.1s / 25 轮`。

**成本侧**：`usage.jsonl` 累计 6,436 次 LLM 调用、**7,347 万 token**（其中输入 7,196 万，
cache 命中 4,899 万）。活跃时段约 **200-760 万 token/小时**。

## 二、问题清单（按严重度）

### P0-1 完结判定只认 4 个"完成"字面 → 连推 3 次空转【框架缺陷】

`core/agent.py` 原逻辑：

```python
if (self.auto_continue and continues < 3 and ...
        and not _re.search(r"测试完成|任务完成|全部完成|已完成", text)):
```

模型实际写的收尾语是「**处理完毕**」「**确认完成**」「**已无剩余步骤，收尾**」「**无需再处理**」——
四个字面一个都不匹配（"完毕"≠"完成"，"确认完成"里没有"任务/全部/已"前缀），于是每一句都被当成"没说完"，
连推 3 次。单次多烧约 **25 万 token**。

### P0-2 `session_token_budget` 被热改成 0 → token 熔断静默失效【配置事故】

`logs/daemon_state.json` 里躺着：

```json
"config": {"review_token_budget": 120000, "session_token_budget": 0}
```

审查器 R4 的判据是 `if budget and used > budget`——**0 是假值**，熔断直接不生效。
配置里明明写着 20 万预算，25 轮 38.8 万 token 也没人叫停。
`review_20261018.jsonl` 22 条审查记录 **verdict 全部为 null**，一次都没拦。

`wake_check_backlog` 也顺带被调成每 12 万 token 才审一次（原 6 万），进一步减少了叫停机会。

### P1-1 服务器广播被当成 @提及 → 误唤醒【daemon 缺陷】

`is_mention()` 的判据是 `bot名 in text`，没有排除无发言人的系统广播：

| 被误判的系统行 | 后果 |
|---|---|
| `<BOT_NAME> is now sleeping. [1/3]` | 睡觉进度，一晚多次误唤醒（18:16、18:46、02:55…） |
| `已将<BOT_NAME>传送至60.5, 70.0, 60.5` | 传送回执，20:23 一分钟误唤醒 3 次 |
| `<PLAYER_A>, <BOT_NAME>.` | 名单/统计行，19:02、02:45 各一次 |

02:55:32 刚结束一次定时唤醒，**02:55:39 立刻又被"is now sleeping"叫醒**跑 9 轮。

### P1-2 清理广播刷满积压 → "无积压不跑"闸门失效【配置缺失】

服务器每 5 分钟刷一轮垃圾清理倒计时（"还剩下 60 秒清理物品和实体"/"清理成功，有192个物品被回收…"），
5 分钟下来几十条。`_scheduled_wake()` 判 `bool(self.backlog)` → **永远非空** →
定时唤醒变成 24 小时每 5 分钟跑一整轮（02:06-02:26 那段"无积压未读，无需运行"是偶发静默期）。

### P2-1 mc_state 摘要白名单过窄 → 反复重查【框架缺陷】

`core/context.py::_dig_mc_state` 只保留 loaded/pos/yaw/pitch/health/dim/gamemode/dead/
looking_at/last_action/food/time/held/chat/players，**丢掉了 screen / window_active /
mouse_grabbed / onGround / effects**。

日志实证：第 1 轮和第 17 轮 agent 都要 `fields:["pos","health","timeOfDay","screen","players",...]`，
摘要回给它 `{"pos":[194.5,77.9,-1116.5],"health":20}`——它明确写下了"**字段被压缩了**"，
然后改用 `mc_act state` / `mc_act time` 重查，每轮多烧一次往返。

附带问题：agent 自己发明的字段名 `timeOfDay`/`canSleep`/`nearbyPlayers` 在 `/state` 里根本不存在
（正确的是 `time.timeOfDay`；`canSleep` 只有 `time` 动作返回），旧摘要静默丢弃，agent 无从察觉。

### P2-2 `file_write` 文档谎称支持 append → 记忆档被反复覆盖、越写越少【文档/实现不一致】

`tools/builtin/mc_bridge.py` 的动作描述写着：

```
file_read(path[,max_chars])、file_write(path,content[,append])、file_append(path,content)
```

但模组侧 `Actions.fileWrite()` **只取 path/content，根本没有 append 参数**（追加是独立的 `file_append`）。
agent 信了文档 → 用 `append=true` → 被忽略 → 变成覆盖 → 于是改成"读回全文+改+覆盖写"。后果：

```
docs/记忆/2026-10-18.md：840 字 → 922 → 522 → 386 → 206 字
（该文件 2026-10-18 分层迁移后位于 `docs/记忆/day/2026-10-18.md`）
```

**原始记录真实丢失**。agent 还把错误结论写进了日档：
「★mc_act file_write 超约 400 字符会被中间压缩丢段落」——这是把
`length`（**字符数**）与 `bytes`（**UTF-8 字节数**）混为一谈得出的幻觉
（386 字节 ≈ 206 汉字，完全正常）。这条错误知识会污染后续每一轮。

### P3 审查器没有"空转"规则【框架缺陷】

R1 连续 3 次同操作失败 / R2 连续 6 次失败 / R3 血量 / R4 token 熔断 / R5 LLM 审查（默认关）。
空转时**所有工具调用都成功**，R1/R2 不触发；R4 又被 P0-2 关掉 → 审查形同虚设。

## 四、还没做的（建议项，需你拍板）

1. **审查器补"空转"规则 R6**：连续 N 轮（如 8 轮）内工具调用全部成功但 `recent_results` 无新状态变化 → 停止。
   目前靠 agent 侧空转刹车兜底，审查侧仍是盲区。
2. **`review_token_budget` 120000 → 60000**：现在每 12 万 token 才审一次，配合 20 万预算，
   最坏能跑到 24 万才被 R4 拦下。改回 6 万更贴合预算。（改 `/config` 热改即可，不用重启）

   夜里无人的时段可以放宽。
4. **客户端加载 15.3 分钟的环境侧缓解**：TLM 每次启动把 1260 个文件/41MB 无条件重拷
   （实测 718,547ms），叠加内存只剩 0.6GB + Defender 逐文件扫描 + PCL2 主客户端常驻 7.25GB。
   建议：加载前关掉 PCL2 主客户端（PID 37348）、给 `<PCL2_DIR>/AI/game` 加 Defender 排除。
5. **记忆档写入规范**：写进 agent 的 SOP——日档一律 `file_append`，禁止 `file_write` 全文覆盖。

## 五、一句话结论

**agent 本身没坏，是"收尾机制 + 唤醒闸门 + 熔断配置"三处同时失效，把它推进了空转循环**：
完结判定漏判 → 连推 3 次；清理广播刷满积压 → 每 5 分钟必跑；token 熔断被热改成 0 → 没人叫停。
三者叠加，一次"看一眼聊天"的定时唤醒烧掉 38.8 万 token。
