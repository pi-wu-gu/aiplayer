# 0.2.1.39 place 放置动作（API 路径）——实现记录

> 版本：0.2.1.39（2026-10-18）｜状态：**已完成并实网验证全绿**（构建/部署/D 组复测均通过）

## 1. 背景：D 组实网测试暴露的按键放置失效

0.2.1.36/0.2.1.37 收尾后跑 D 组（放置联动）实网测试，结论：**按键路径（press/keys key.use）放置
在窗口非前台状态下完全失效**。证据链：

1. `look`/`look_lock` 视线断言 PASS：`looking_at={"block":"minecraft:grass_block","pos":[6,70,-14],"face":"up"}`，
   aim=(6.5,71,-13.5) pitch=68.26——**模组自算的视线是对的**；
2. 但 `key.use` 之后目标格仍是空气。多变体全败：`press key.mouse.right` / `press key.use` /
   `keys key.use 500/1200ms` / `lock+keys 800ms`；
3. 对照实验：`press key.inventory` **正常打开 InventoryScreen** → `KeyMapping.click` 机制本身有效；
4. 源码定位：`lookingAt()` 用 `p.pick(6.0, 0.0f, false)` **自算**，而 use 键实际依赖
   `mc.hitResult`（相机插值/窗口状态耦合）——**两套不是一套**。与 dig 的历史教训
   （`docs/记忆/2026-10-17-挖方块诊断.md`）同源：按键链路不可靠，API 路径才行。

## 2. 用户关键输入（2026-10-18）：玩家有碰撞箱，不是质点

设计评审时用户提醒：**"玩家位置不仅是一个点，还有碰撞箱范围，会影响放置"**。落到实现上
有三层含义：

1. **实体碰撞校验**：服务端放置时用 `CollisionContext.of(player)` 校验新方块与玩家身体
   （AABB 宽 0.6 高 1.8）是否重叠，重叠必然驳回。D 组的真实场景正是如此：玩家脚底 y=71，
   目标格 (6,71,-14) 的 AABB 与玩家 AABB **重叠**——即使早做 API 路径也一样放不进去，
   正确动作是先 move 走开或换目标格；
2. **距离校验也基于身体**：服务端 `canInteractWithBlockAt(support, 1.0)` 是
   `脚底 → 支撑格底中心 ≤ block_interaction_range + 1`（不是"眼睛到点"的射线语义）；
3. **给模型的报错必须带数值**：光说"放不了"模型只能瞎试；报错里同时给目标格 AABB、
   玩家 AABB、脚底坐标，模型才能自我校正（走开/跳起/换格）。

## 3. 实现

### 3.1 新增 `place` 动作（Drivers.startPlace，主线程发起即返回）

- **发包路径**：主线程内自算 `BlockHitResult`（点击点=支撑格被点击面的面中心，
  方向=该面法线，服务端据此算放置位 = `clickedPos.relative(face)`）→
  `mc.gameMode.useItemOn(player, hand, bhr)`。与真实玩家右键**同一条链路**，
  服务端照常跑事件/领地保护/距离/实体碰撞校验；不经按键注入，不受鼠标抓取/窗口前台门禁影响。
- **两段式协议**（同 dig，避免 `runOnClientThread` 闩锁死锁——动作体绝不能阻塞等 tick）：
  `place` → `place_sent`（附 target/support/face/hand/support_dist/player 位姿）；
  3 tick 后 `tickPlace()` 自动确认 → `place_status`（别名 `place_state`，只读常驻）查
  `place_placed`（附 landed）/ `place_failed`（附 detail 诊断）/ `place_unverified`
  （超 10s 未确认：游戏暂停/界面开着/tick 停滞）。也可 `block_at` 复核。
- **★碰撞箱预检**（发起前）：`player.getBoundingBox().intersects(new AABB(target))` →
  直接报 `place_err:`，带双方 AABB 数值 + 脚底坐标 + "先 move 走开/跳起或换目标格"。
- **支撑面自动选择**：省略 `side` 时按 下方地板(up) → 四周墙 → 上方天花板(down) 顺序
  找第一个可用支撑格，跳过：空气 / 流体 / 无碰撞体积 / 带 BlockEntity（箱子·工作台·熔炉）/
  常见非 BE 交互方块（按钮·拉杆·门·活板门·音符盒·蛋糕·床·钟·比较器·中继器·
  日光探测器·绊线钩·花盆·命令方块·龙蛋·末影门户框·重生锚）；
  距离用服务端同款尺子（脚底→支撑格底中心 ≤ block_interaction_range+1）。
  `side=` 显式指定时不避让交互方块，但回显 `support_interactive:true` 警告
  （右键可能先开界面而非放置）。
- **发起前校验**（全部明确报错，不让模型瞎猜）：界面打开中 / 使用物品中 / 已死亡 /
  手持非方块（回显当前手持 id）/ 物品冷却中 / 冒险·旁观模式（mayBuild）/
  目标格已有方块（空气与可替换物除外）/ 支撑格是空气 / 支撑格超距。
- **失败诊断**（tickPlace 收集）：手持已变 / 冷却中 / 模式不允许 / 界面开着 /
  支撑格被挖 / 支撑面带界面 / 玩家放置期间挪进目标格 / 兜底"服务端驳回"提示。
- **权限轴**：与 press/keys/dig 同轴——`gameActionMode=safe` 起 place 不注册
  （GATED 集合同步加 place/place_block/put_block）；place_status 只读常驻。

## 5. 已知边界（写进文档，不算缺陷）

- 按键放置（look+keys key.use）**仍然不可靠**（hitResult 与 pick 不是一套）——放置一律用 place 动作；
- 交互性支撑面（未收录进 INTERACTIVE_HINTS 的模组方块）可能触发交互而非放置 →
  place_status 的 detail 会点明，换 side= 即可；
- 非全方块（台阶/地毯/火把）的碰撞形状小于整格，碰撞箱预检按整格算可能误拦
  （保守方向，报错信息可自证）；
- place 不自动中断 look_lock（放置不依赖视角，两者不冲突）。

## 6. 客户端加载卡点分析（2026-10-18，用户要求"确认加载缓慢原因"）

本次 02:28:05 启动 → 02:43:24 控制面就绪，总耗时约 15.3 分钟。线程转储 + 日志定位：

- **卡点 = touhou_little_maid 的 `CommonDefaultPack.initCommonDefaultPack()`**：
  02:30:46 `common default pack init start...` → 02:42:45 `finished, cost time: 718547 ms`
  （**718.5 秒**；上次 0.2.1.38 加载为 668.9 秒——稳定复现，非本次回归）。
- **它做什么**（反编译 `entity/info/CommonDefaultPack.class` + `util/GetJarResources.class`）：
  每次启动都把 jar 内默认资源包 **1260 个文件 / 41MB** 无条件重拷
  （`Files.copy(..., REPLACE_EXISTING)`，无"已存在则跳过"）到
  `game/tlm_custom_pack/touhou_little_maid-1.0.0/`；且跑在 modloading-worker 上，
  阻塞 FML 并行加载的汇总屏障 → 整个 mod 加载阶段等它。
- **为什么拷 1260 个文件要 12 分钟**：同文件树现在 `cp -r` 只要 13 秒（10ms/文件），
  游戏中是 570ms/文件。差距来自环境而非代码：
  1. **物理内存耗尽**：本机内存几乎耗尽（空闲仅剩个位数百分比，提交内存逼近上限），系统持续换页，
     拷贝的每次缓冲分配/GC 都吃缺页开销（JVM -Xmx7168m + 主客户端进程常驻数 GB + 长时间运行占 1 核）；
  2. Windows Defender 实时扫描每个写入文件；
  3. 磁盘（NVMe SSD）本身不是瓶颈。
- **非死锁证据**：卡点期后线程转储显示 16 个 modloading-worker 全部
  `ForkJoinPool.awaitWork` 空闲、无任何 socketRead、Render thread 在
  `ModLoader.waitForTask` 等屏障；日志里的 SSLFlowDelegate 栈是 Railways
  披风下载失败的已完成异常（红鲱鱼）。pack init 一结束，其余加载
  （资源重载/进世界）只用了约 3.5 分钟。
- **可行动结论**（属整合包/环境问题，模组无需改）：① 加载前关掉或重启
  PCL2 主客户端（PID 37348，7.25GB+1核）；② 如常驻则给
  `<GAME_DIR>` 加 Defender 排除；③ TLM 默认包重拷无法从
  模组侧跳过（第三方模组无配置项），只能让环境不拖后腿。
