# 环境检测 + 位置/实体/玩家动态记录 · 可行性分析

- **分析日期**：2026-10-18
- **需求原文**：「添加 agent 每轮对话周围环境检测（设定范围默认 5×5×5）及 AI 玩家自身位置变化连续记录（限制记录时长限制），添加观察实体动态（主动触发并读取）、玩家动态（自动记录，主动读取），均限制可调的默认记录时长，不保存过期数据」
- **结论**：**整体可行，且与现有架构高度同构**。四种子功能中两个高可行度（位置轨迹、玩家动态）、一个中高（每轮环境检测，关键是摘要压缩）、一个中（实体动态，关键是差分事件化）。建议分两期实施。

---

## 一、需求拆解

| # | 子功能 | 触发方式 | 读取方式 | 记录时长 |
|---|---|---|---|---|
| A | 周围环境检测（默认 5×5×5） | **每轮对话自动** | 随轮次注入 prompt（无需主动读） | 瞬时快照，无历史 |
| B | 自身位置变化连续记录 | **常驻自动采样** | 主动查询（游标/全量） | 限时长，默认可调 |
| C | 实体动态观察 | **主动触发**（start）→ 停止（stop） | 主动读取 | 限时长，默认可调 |
| D | 玩家动态 | **常驻自动采样** | 主动读取 | 限时长，默认可调 |

横切要求：① 记录时长**默认值可调**（配置 + 动作参数双层）；② **不保存过期数据**（滑动窗口淘汰，非"存了但过滤"）。

## 二、可行度总评

| 子功能 | 可行度 | 主要依据 | 主要风险 |
|---|---|---|---|
| A 每轮环境检测 | ★★★★☆ 高 | `state()` 已有大半字段；`entities`/`players` 动作证明查询 API 成本低；agent 侧 `ChatBuffer` 每轮注入是现成范式 | **token 成本**——125 格全量列表 ~700 token/轮必须压缩为聚合摘要 |
| B 位置轨迹 | ★★★★★ 很高 | `ChatBuffer`（环形+游标+落盘）可直接变体；`onClientTick` 采样零额外架构 | 数据量控制（采样间隔 × 时长） |
| C 实体动态 | ★★★☆☆ 中高 | `entities` 动作同款 `level.getEntities` API；`Entity.getId()` 网络 id 稳定可做轨迹关联 | **差分事件化设计**——全量快照会爆炸；静止实体不能反复记 |
| D 玩家动态 | ★★★★☆ 高 | `nearbyPlayers` + `connection.getOnlinePlayers()` 两个现成数据源；与 C 同构可共用采样器 | Tab 列表全服玩家量大时要限流 |

## 四、逐项设计草案

### A. 每轮环境检测（默认 5×5×5）

**模组侧**——新动作 `env_scan`（只读，不过权限轴）：

```
{"type":"env_scan","range":5}   → 以玩家脚部方块为中心的 (2R-1)³ 范围（R=5 → 9×9×9？见下方框说明）
```

> ⚠ 语义澄清：「5×5×5」按字面 = 以玩家为中心的 5³=125 格（-2..+2）。默认取字面 5³，range 参数可调。

**摘要格式（压缩是关键）**：
```json
{"center":[x,y,z],
 "counts":{"minecraft:air":98,"minecraft:stone":12,"minecraft:grass_block":6,...},
 "notable":[{"id":"minecraft:chest","pos":[..]},{"id":"minecraft:oak_sign","pos":[..]}],
 "fluid":[{"id":"minecraft:water","pos":[..]}],
 "below":"minecraft:grass_block","dim":"minecraft:overworld"}
```
- **聚合计数**：普通方块按 id 计数（125 格通常只剩 5-15 种，~200 字符 ≈ 60-100 token）
- **notable 单列**：容器/告示牌/门/熔炉/ notable 方块实体逐格列（这类才需要精确坐标）
- **流体/危险单列**：水/岩浆/火/仙人掌
- ★**绝不做 125 个 id 的全量平铺**（~2KB/700 token/轮，12 轮烧 8.4K——这正是历史上白烧 token 的事故模式）

**agent 侧**——`Agent.step` 每轮前注入（仿 chat_buffer）：

```
【环境快照】中心(196,77,-1106) 脚下=grass_block | 计数: air×98 stone×12 grass×6
|  notable: 无 | 流体: 无 | 维度: overworld
```

- 注入位置：`core/chat_buffer.py` 的每轮推送钩子旁（同一次 mc_bridge 调用批量拿，不新增 HTTP 往返）
- 与【游戏聊天栏推送】同性质：**环境信息不是用户指令**（PRIMARY_PROMPT 已有一条同类声明，照抄）
- 可配置开关：`[watch].env_per_round`（默认 true）+ `[watch].env_range`（默认 5）

### B. 自身位置变化连续记录

**模组侧**——`PosTrack` 环形缓冲（`ChatBuffer` 变体，仅内存不落盘——位置历史跨重启无意义，且「不保存过期数据」）：

- 采样：`onClientTick` 里按 `pos_sample_interval_ms`（默认 500ms）记 `{t, pos:[x,y,z], yaw, dim}`
- 优化：**位移/转角低于阈值不记**（站定不动时缓冲不增长——避免 0.5s×10min=1200 条原地重复）
- 淘汰：入队时 `peekFirst` 检查时间戳，超 `pos_retention_ms`（默认 600000=10min）直接丢弃
- 查询动作 `pos_track`：`{"type":"pos_track","since":<id>,"limit":50}` → 增量游标（与 /chat 的 since 语义一致）

**数据量**：移动中 0.5s/条 × 10min ≈ 1200 条 × ~70B ≈ 84KB 内存，可忽略。

### C. 实体动态（主动触发并读取）

**模组侧**——`EntityWatch`：

```
{"type":"entity_watch","start":true,"radius":16,"interval_ms":1000,"retention_ms":600000}
{"type":"entity_watch","read":true,"since":<id>}     ← 增量读
{"type":"entity_watch","stop":true}
```

- 采样：start 后在 tick 钩子按 interval 对 `box` 内实体采样，按 `Entity.getId()` 关联轨迹
- **差分事件化**（核心设计）：只记「事件」不记快照——
  - `appeared`（新 id 出现）/ `gone`（消失）
  - `moved`（位移 > 阈值，如 1 格，记新位置）
  - 静止实体**零记录**（一个 10 分钟不动的牛 = 1 条 appeared + 0 条 moved）
- 环形缓冲存事件（带时间戳 + retention 淘汰）；`read` 支持游标增量
- 同时最多 1 个 watch（与 look_lock 单任务槽一致，新 start 取代旧的）

**数据量估算**：半径 16 格 50 实体、其中 20 个在动，1s 间隔 × 10min = 600 次采样 → 事件数 ≈ 20 moved/s × 600 = 12000 条峰值。偏大——缓解：moved 事件默认带 `min_move`（默认 1.0 格）且同实体同方向连续移动可合并（每实体每采样周期最多 1 条）；实际场景（基地周边）实体数通常 <20，事件 ~2000-4000 条 × ~90B ≈ 300KB，可接受。**上限保护**：环形缓冲硬顶 5000 条，超出丢最旧。

### D. 玩家动态（自动记录，主动读取）

**模组侧**——`PlayerTrack`（常驻，无需 start）：

- 每 `player_sample_interval_ms`（默认 1000ms）采样两个源：
  - 附近实体玩家（name/pos/dist/health 摘要）
  - Tab 列表变化（`getOnlinePlayers()`：上线/下线/换维度/ping 突增）——**只记变化事件**
- 事件类型：`join`/`leave`/`near_appeared`/`near_gone`/`moved`/`dim_change`/`ping_spike`
- 查询 `player_track`（同 pos_track 游标语义）；retention 默认 10min

**与 C 的关系**：D 的采样器与 C 同构，可抽一个公共 `TrackBuffer` 基类；D 常驻自动、C 显式开关，差别只在生命周期。

### 横切：可调时长 + 不保存过期数据

- **配置**（`config/aiplayer-common.toml` 新增 `[watch]` 段）：
  ```toml
  [watch]
  enabled = true                    # 总闸（false 则 tick 采样器全不注册）
  env_per_round = true              # A：每轮注入
  env_range = 5                     # A：环境检测边长（格）
  pos_interval_ms = 500             # B：位置采样间隔
  pos_retention_ms = 600000         # B：位置记录保留（10 分钟）
  player_interval_ms = 1000         # D：玩家采样间隔
  player_retention_ms = 600000      # D：玩家动态保留
  entity_radius = 16                # C：实体观察半径
  entity_retention_ms = 600000      # C：实体动态保留
  ```
- **动作参数可覆盖**：`interval_ms`/`retention_ms` 每次调用可传（夹在合理区间，如 retention 60s-1h）
- **「不保存过期数据」三层落实**：① 入队时时间戳淘汰（不是查询时过滤）② 全内存、不落盘（落盘=变相永久保存）③ retention 参数本身也可调——用户要更短窗口就调更短

## 五、成本与风险评估

| 维度 | 评估 |
|---|---|
| **token 成本** | A 每轮 ~60-100 token（聚合版）；若误用全量平铺 ~700/轮——**必须在实现评审时卡住摘要格式**。B/C/D 纯工具查询，不注入则不花 token |
| **客户端性能** | tick 采样：位置/玩家 O(1)~O(附近玩家数)；实体采样每 1s 一次 `getEntities`（entities 动作已在用同 API，实测低开销）。大型实体农场（100+）时 C 的 getEntities 成本上升——默认半径 16 + 事件化 + 5000 条硬顶三重控制 |
| **主线程约束** | 全部采样挂 `onClientTick`（主线程），与 dig/look_lock 同模式；单次采样须 < 1ms 级，事件化差分静止零成本 |
| **内存** | B ~84KB + C ≤450KB + D ~100KB ≈ **< 1MB**，可忽略 |
| **与 agent 进程解耦** | 模组侧 tick 采样不依赖 sidecar 存活——agent 没醒的时段也在记，醒来读滑动窗口（这正是「daemon 定时唤醒」场景的价值：唤醒即可得"刚才发生了什么"） |
| **权限表** | A/B/C/D 全只读，**不过权限轴**（与 dig 相反）；C 的 start 是"开始观察"仍不改世界，不进门控 |
| **与截图约定的边界** | ⚠ 需用户知情：项目约定「截图仅是可调用功能、不自动进决策回路」；本需求的 A 明确要求**每轮自动注入**，是新指令、覆盖该精神——但仅限文本环境摘要（不涉图像），且保留 `env_per_round` 开关可一键关回 |

## 七、分期实施建议

### 一期（低风险高价值，估时 1 个构建周期）
- 模组：`env_scan` 动作（聚合摘要）+ `PosTrack` + `pos_track` 动作 + `[watch]` 配置段 + tick 采样挂点
- agent：每轮【环境快照】注入 + PRIMARY_PROMPT 说明 + mc_act manifest 补组
- 验收：部署后实网验证——12 轮任务每轮都有快照、token 增量 <100/轮、位置轨迹游标可读

### 二期（实体/玩家动态，估时 1-2 个构建周期）
- 模组：`TrackBuffer` 基类 + `EntityWatch`（start/read/stop）+ `PlayerTrack` + `player_track`/`entity_watch` 动作
- 重点攻克：差分事件化的正确性（id 复用/维度切换/区块卸载的 gone 误报——实体卸载 ≠ 消失，要用「 unloading 宽限」）
- 验收：基地周边挂机 10 分钟，事件数与手动观察对账；杀怪/刷怪场景 appeared/gone 计数吻合

## 九、总结

- **架构上完全可行**：四种子功能都是已有零件（ChatBuffer 范式 / Drivers 三段式 / entities-players 查询 / chat_buffer 每轮注入）的组合，无新机制突破
- **两个真正的设计难点**：① 环境摘要的 token 压缩（必须聚合、禁全量平铺）② 实体动态的差分事件化（禁快照式记录）
- **两个必须守住的边界**：① tick 采样单次成本 <1ms 级 ② 全内存不落盘 + 入队淘汰，真正兑现「不保存过期数据」
- 建议一期先落地 A+B（每轮环境 + 位置轨迹），二期再做 C+D（实体/玩家动态）
