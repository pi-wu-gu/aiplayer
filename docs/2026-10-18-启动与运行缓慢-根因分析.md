> ① 运行慢**不是**堆耗尽，是 FTB Chunks 地图锁（已实证修复）；
> ② Defender 排除对启动的影响**不稳定**，第三次实测反而更慢——见下表。

## 摘要

| | 现象 | 主因 | 处置效果 |
|---|---|---|---|
| **启动慢** | 卡在 `common default pack init` 8-19 分钟 | TLM 每次启动**无条件重拷 1260 个文件**（无跳过判断）；耗时随系统 IO 负载剧烈波动 | Defender 排除：813.8s → 471.8s → **1113.6s**（三次实测，**helpful but unstable**） |

## 一、启动慢：813 秒卡在 TLM

### 证据

```
06:34:00.941  [touhou_little_maid/]: common default pack init start...
06:47:34.792  [touhou_little_maid/]: common default pack init finished, cost time: 813829.86 ms
```

- 这 13.6 分钟内**日志完全不动**（1835 行 → 1835 行），整个 FML 加载屏障被卡住
- 处理量：**1260 个文件 / 41MB**
- 折算：**645 ms/文件** —— 而 NVMe 顺序写 41MB 本应是 0.02 秒量级

### ★根因（2026-10-18 10:40 基准测试修正：瓶颈不在磁盘，在 FML UnionFileSystem）

**基准测试（同一台机、同一个 jar、1260 文件）**：

| 路径 | 耗时 | 折算 |
|---|---|---|
| Python `shutil.copytree`（磁盘→磁盘） | 1.24 s | ~1 ms/文件 |
| **Java `jdk.nio.zipfs` walk+copy（TLM 同构代码）** | **0.96 s** | **0.8 ms/文件** |
| 游戏内 TLM 实测（三次） | 471.8 / 813.8 / 1113.6 s | **374-884 ms/文件** |

**差 400-1000 倍。** 且文件 mtime 实测集中在 **1-2 分钟内**写完——真正的拷贝在游戏里也很快，
StopWatch 报的十几分钟大头花在别处。

**真根因：`GetJarResources.copyFolder` 走了 FML SecureJar 的 UnionFileSystem（反编译实证）**

```java
URL url = TouhouLittleMaid.class.getResource("/assets/touhou_little_maid/tlm_custom_pack/…");
Path src = Paths.get(url.toURI());      // ← MC 里返回 UnionFileSystem 路径（不是 jdk.zipfs）
Files.walk(src).forEach(Files.copy(p, out, REPLACE_EXISTING));   // 每条都过 UnionFileSystem
```

UnionFileSystem（cpw.mods.securejarhandler）每次 open/stat 都要做 union 路径解析、
包归属定位与安全校验，单次开销是 jdk.zipfs 的**数百倍**——这正是 374-884 ms/文件的来源。
我独立复现时手动挂的是 `jdk.nio.zipfs.ZipFileSystem`（0.8 ms/文件），所以快了三个数量级。

**Defender 的 342 秒差异仍是真实的**（813.8→471.8），但它只是叠加在 UnionFileSystem 之上的放大器；
第三次 1113.6s 说明系统负载波动主导，**它不是稳定可控的收益**。

### 优化方案（按收益排序）

| 方案 | 原理 | 收益 | 成本/风险 |
|---|---|---|---|
| **A. mixin patch：目标已存在则跳过** ⭐推荐 | 小 mixin mod 注入 `GetJarResources.copyFolder` HEAD：目标目录文件数 ≥1000 且 TLM 版本未变 → 直接 cancel。首次启动正常全拷，之后每次 <1s | **每次启动省 8-19 分钟** | 一次性写个小 mod（~100 行）；TLM 更新时靠版本 marker 自动重拷一次 |
| B. 禁用 TLM | 不加载模组 | 15 分钟 → 0 | 存档女仆失效 |
| C. 环境缓解（Defender 排除/关程序） | 已做 | 不稳定（813/471/1113 证明） | — |
| D. RAM disk / 换盘 | — | **无效**（瓶颈不是 IO，是文件系统协议层） | 不采用 |

> ⚠️ 之前写"Defender 排除 −42%"是单次对比的巧合，第三次实测（1113.6s 比排除前还慢）推翻了它。

## 二、运行慢：FTB Chunks 地图锁把主线程饿死（**不是堆的问题**）

> ⚠️ 本节经过两轮修正。第一版以为是"堆耗尽"，重启后**堆很健康却仍卡**，
> 抓线程转储才拿到真因。以下为最终结论。

### 现象

| 项 | 观测 |
|---|---|
| 动作 | `time`/`block_at`/`get_inventory`/`scan_region` **全部 20s 超时** |
| `/state` | 3.9-20s 才返回，或直接返回空 |
| 堆 | **5.1-6.0GB / 7.0GB（73-85%），有年轻代** → 完全健康 |
| 磁盘 | **活动 1.7%，队列长度 0** → 完全没有饱和 |
| CPU | java 工作集 10GB，CPU 累计正常 |

**堆、磁盘、CPU 三个常见嫌疑全部排除**——这正是必须抓转储的原因。

### 真因：主线程 BLOCKED 等一把地图锁

两次转储（间隔约 3 分钟）指向同一把锁 `0x0000000763000000`：

```
"Render thread"  BLOCKED (on object monitor)
  at dev.ftb.mods.ftbchunks.client.map.MapManager.getDimensions(MapManager.java:186)
  - waiting to lock <0x0000000763000000>
  at MapManager.getDimension(MapManager.java:192)
  at FTBChunksClient.lambda$findVisibleWaypoints$9(FTBChunksClient.java:1042)

（另一次栈走的是渲染区块更新的路径）
  at MapDimension.getRegion(MapDimension.java:142)
  at UpdateChunkFromServerTask.runMapTask(...)
  at ClientTaskQueue.runQueuedTasks(...)
```

锁的**持有者**是地图后台线程，卡在同步读盘：

```
"pool-26-thread-1"  RUNNABLE
  at java.nio.channels.FileChannel.open(FileChannel.java:309)
  at javax.imageio.ImageIO.createImageInputStream(ImageIO.java:357)
  at javax.imageio.ImageIO.read(ImageIO.java:1359)
  at dev.ftb.mods.ftbchunks.client.map.MapRegionData.read(MapRegionData.java:113)
  at MapRegion.getDataBlockingNoSync(MapRegion.java:81)
  at MapRegion.getDataBlocking(MapRegion.java:72)
```

**因果链**：

1. FTB Chunks 的 `MapRegion.getDataBlocking()` 用 **`ImageIO.read`（同步阻塞）** 读地图区域文件，
   且**持有维度级锁**
2. 主线程**每个 tick** 都要拿同一把锁（渲染路径点 / 更新区块地图）
3. 于是主线程每 tick 都在等锁 → 一帧都过不去 → `mc.execute()` 的动作队列永不执行
4. 所有 `/command` 动作卡满 20 秒 latch 超时

### 为什么读盘会慢（磁盘却是空闲的）

bot 自己的地图数据：`local/ftbchunks/data/82b7d738-…/` → **333 个 region 文件 / 3.8MB**。
冷启动后 region 缓存为空，需要逐个读并解码；单次 `FileChannel.open + ImageIO.read` 在这个环境里
被拖到**秒级**（观测到同一调用持续 2-3 分钟仍未返回），而磁盘计数器却显示 1.7%。

这说明开销不在「磁盘吞吐」，而在**文件打开/解码路径上的等待**（杀软过滤驱动、NTFS 元数据、
或 `ImageIO` SPI 探测）。三个常见层（磁盘/CPU/堆）都不是瓶颈。

### 与 0.2.1.40 的关系：**无关**

0.2.1.40 只改了 `ControlServer` 的 `ok` 判定 + 内嵌 bundle（agent 侧）。
本次卡住的是 **FTB Chunks 的客户端地图线程与主线程抢锁**，与模组改动没有调用关系。

### 为什么 0.2.1.39 跑了 3.8 小时没事

那 3.8 小时里地图 region 已全部读进内存（缓存命中），不存在冷启动时的集中读取。
**这次每次都是冷启动**（刚重启 / 刚换 jar），所以必现。

### 修复方案

| 措施 | 原理 | 风险 | 建议 |
|---|---|---|---|
| **备份后移走 bot 的 region 数据**（`local/ftbchunks/data/*/`） | 读取量 355 → 0，地图从当前位置重建 | 丢失历史地图（已备份 355 文件） | ✅ **已执行并验证成功**（见文末） |
| 关闭客户端地图记录 | 减少 region 写入与读取 | FTB Chunks 无总开关，需改 `local/ftbchunks-client.snbt` 或改代码 | 次选 |
| 移除 FTB Chunks 客户端模组 | 彻底消除该锁 | 服务端领地/地图功能受影响 | 极端 |
| **加物理内存** | region 能常驻页缓存，冷启动也快 | 硬件成本 | 根治 |
| **定期清理 region**（比如每周一次） | 防止累积回 300+ 文件再次触发 | 需脚本化 | 建议（见下方⚠️） |

### ★已验证：移走地图数据 → 主线程恢复

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `time` 动作 | **20s 超时**（无返回） | **653 ms，`ok=true`** |
| `scan_region` | **20s 超时** | ✅ 通过 |
| `get_inventory` | **20s 超时** | ✅ 通过 |
| `/state` | 3.9-20 秒 / 返回空 | 0.69-0.79 秒，1777 字符 |
| 0.2.1.40 验收 | 卡在 F 段 | **34 / 34 全绿** |

**根因确认**：`local/ftbchunks/data/` 的 355 个 region 文件（3.9MB）让 FTB Chunks 在地图线程里
长时间持锁同步读盘，主线程每 tick 抢同一把锁被饿死。清空后读取量归零，立刻恢复。

> ⚠️ **会复发**：清空后客户端已重新生成 62 个 region（跑了 2.5 小时）。
> 按这个增速，累积回 300+ 只是时间问题，届时**可能再次卡住**。
> 建议：写个定时任务把 `data/` 里的旧 region 定期挪进 `data_backup_<日期>/`
> （只保留最近 N 天），或长期看是否值得加内存/换掉 FTB Chunks。

## 二·B ★运行期持续刷 GL 错误：489MB 日志 / 193 万行（10:38 发现，比解压更急）

```
latest.log 总行数 1,932,546 —— 其中 1,927,323 行（99.76%）是：
[Render thread/INFO] [com.mojang.blaze3d.platform.GlDebug/]: OpenGL debug message:
  id=1281, source=API, type=ERROR, severity=HIGH,
  message='GL_INVALID_VALUE error generated. Invalid texture format.'
```

- 从 **07:46:52（进世界渲染后第一秒）** 起持续刷到现在（10:38 仍在刷，tail 50 行全是它）
- 日志文件 **489.5 MB 且还在涨**——每条都是同步落盘，每帧几十条，磁盘/主线程都在陪跑
- 上一次卡死（0.2.1.39 末期）日志停写前刷的也是同一个错误——**两次故障它都在场**

### 根因开关（反编译实证，比找坏纹理先落地）

`Options` 的 `glDebugVerbosity` **原版默认值 = 1**（1.21.1 字节码 `iconst_1; putfield u:I`），
即 **GL debug 回调默认开启**；AI 实例的 `options.txt` 里没有这一行 → 用默认 → 回调开着。
某模组有坏纹理（格式非法）→ 每帧报 `GL_INVALID_VALUE` → 每条同步写日志。

**修复（一行）**：客户端**关闭时**在 `options.txt` 追加一行：

```
glDebugVerbosity:0
```

游戏运行中改会被保存时覆盖，必须在关客户端后改。已写脚本 `AI/launcher/fix_gl_verbosity.py`
（幂等，可挂启动前）。

### 长线

`Invalid texture format` 的来源要二分模组定位（某模组用了非法纹理格式/尺寸）。
关掉 verbosity 后错误仍发生只是不再打印——GPU 侧开销仍在，但同步日志写没了，收益已占大头。

### ❌ 发现的问题

**1. ★继承的用户配置被 bundle 默认值覆盖（模组侧真 bug，已手工规避）**

`AgentSidecar.deployTo()` 的顺序：

```java
if (fresh) inheritFromPrevious(...);   // ① 先继承旧的 config/keys/logs
unzip(zipFile, target);                // ② 再把 bundle 解压进去 —— 覆盖了 ①
```

bundle 里含 `agent/config/config.yaml`（默认值），于是 **① 继承来的真实配置被 ② 覆盖**。
`keys.yaml` 和 `logs/` 侥幸保住，因为它们在 `EXCLUDE_PARTS` 里没进 bundle。

实测后果：
- `roots.shared` 变成 `"<GAME_DIR>/aiplayer"` 占位符 → 文件工具指向不存在的目录

已手工改回真实值（`diff` 确认只有这两行不同）。**代码待修**：把 `inheritFromPrevious`
移到 `unzip` 之后即可（`copyTree` 用 `REPLACE_EXISTING`，能正确覆盖）。
`preserveAndClear` 分支同理（它先把用户数据放回、再被 unzip 覆盖，且备份已删 → 无法恢复）。

**2. `/state` 响应 3.9-13 秒、部分动作 20s 超时**

### FastPack 工程要点（`minecraft mod/tlm_fastpack`）

- 注入 `GetJarResources.copyFolder` HEAD（`@Pseudo` + `require=0`，目标是 mod 类无需 refmap）
- 跳过条件：磁盘 ≥1000 文件 + marker 版本一致 + jar 条目数/总字节一致（zip 中央目录）+ 磁盘数与 marker 一致
- **v1.0.0 实测踩坑两处**：
  ① jar 定位：`getProtectionDomain().getCodeSource()` 在 SecureJar 下返回 `union:` URI，
  `Paths.get()` 直接炸 → 改用 `ModList.get().getModFileById(id).getFile().getFilePath()`
  （`IModFileInfo` 在 `neoforgespi.language`、接口方法名是 `getFilePath()` 不是 `getFile()`）
  ② 静默分支害人：jar 定位失败时 v1.0.0 无任何日志，排查绕一圈 → 现在每个分支都记 INFO/WARN
- **验证方式**：marker 预种子（python 算 jar+磁盘统计写入 Properties 格式）→ 首次带补丁启动即跳过
- **观察**：全量拷贝耗时波动巨大（50.6s 与 13+ min 各出现过一次）——首启前若同内容刚被写过
  （OS 缓存热）会快一个量级；这正是"跳过"比"优化拷贝"更可靠的实证
- 另：Sodium 的 NvidiaWorkarounds 会强制开 `GL_DEBUG_OUTPUT_SYNCHRONOUS`，但 verbosity=0 时
  MC 不装回调 → 日志刷屏照样止住（实测 0 条）
