# TLM 默认包拷贝 · 剩余优化方案分析

> 2026-10-18 · 前提：`tlm_fastpack` v1.0.0 已上线，跳过覆盖了绝大多数启动。
> 本文分析**仍会触发全量拷贝的场景**还能怎么提速。

## 一、现在还有哪些场景会触发全量拷贝

| 场景 | 频率 | 现状耗时 |
|---|---|---|
| ① 首次安装 / 换机 | 一次性 | 50s ~ 21.8min（波动极大，取决于 OS 缓存冷热） |
| ② TLM 升级（版本号变化） | 每 次 TLM 更新 | 同上 |
| ③ 用户点 reset（模组设置） | 手动 | 同上 |
| ④ 目录损坏 / 误删 | 意外 | 同上 |

四个场景共享同一条慢路径：上游 `copyFolder` 走 UnionFileSystem，逐文件 300-900ms。
**注意：这些场景下磁盘写入本身只要 1-2 秒（基准已证），慢的全在文件系统协议层。**

## 二、两个已核实的技术前提（本分析的基石）

1. **上游只覆盖、从不删除**——`copyFolder` 字节码中 0 处 delete，逐条 `Files.copy(REPLACE_EXISTING)`。
   ⇒ **"只拷差异"与"全量覆盖"的最终产物完全等价**（多出来的磁盘文件两边都会保留）。
2. **zip 中央目录自带每条目的 size + CRC32**——不用解压就能拿到内容指纹。
   ⇒ 逐条比对成本 = 读 41MB 磁盘算 CRC（约 0.3-0.5s）+ 读中央目录（毫秒）。

## 三、方案矩阵（按推荐度）

### ★方案 1：增量同步替代全量拷贝（v1.1，强烈推荐）

mixin HEAD 的决策从二态改三态：

```
内容未变            → cancel（现状，已有）
内容需更新          → cancel + 自己用 ZipFile 做增量同步（新）
无法判定/同步失败    → 放行上游（兜底，已有）
```

增量同步实现：遍历 zip 条目（前缀过滤）→ 与磁盘文件比对 **存在性 + size + CRC32** →
只拷缺失/不一致的条目（`ZipFile.getInputStream` → `Files.copy`，走普通文件 IO，不走 UnionFileSystem）。

| 场景 | 现状 | 增量同步后 |
|---|---|---|
| 首次安装 | 8-19 min | **~2s**（1260 条全要拷，但走 ZipFile 直读） |
| TLM 升级 | 8-19 min | **<1s**（通常只改少量文件） |
| reset / 目录损坏 | 8-19 min | ~2s |
| 内容未变 | 0.8s | 0.8s（不变） |

- **语义等价**：由前提 1，最终产物与上游一致，不改变任何 TLM 行为
- **成本**：CRC 比对 +0.3-0.5s/次；代码 ~80 行（复用现有 jar 定位与 marker 基建）
- **风险与兜底**：同步中途异常 → 目录处于中间态 → marker 不写 → 下次重新同步（自愈链不变）；
  任何意外都还可放行上游
- **验证方法**：reset 一次，对比增量产物与上游产物（文件数、总字节、抽样 CRC）

### ★方案 2：放宽"TLM 版本变化必全拷"（与方案 1 叠加）

现在 TLM 升版本 → 强制全拷（保守）。但 marker 已存 jar 侧内容指纹（条目数+总字节）——
**TLM 升级但默认包内容没动时，本可直接跳过**。配合方案 1 的 CRC 清单，
可升级为"逐条 CRC 指纹清单存 marker"：内容真变了才同步，变几条拷几条。

- 风险：内容变化但条目数+总字节+CRC 全都不变 → 漏更。概率趋近于零（CRC32 碰撞 + 尺寸巧合同时发生）
- 收益：TLM 升级场景从"一次全拷"变成"通常 0 拷"

### 方案 3：并行拷贝（叠加项，收益小）

上游单线程串行。方案 1 的 ZipFile 直读路径可用 4 线程并行写——但增量同步后通常只剩
个位数文件要拷，并行的意义只剩首次安装（2s → 0.8s）。**不建议做**，复杂度不值。

### 方案 4：给 TLM 上游提 issue（零维护）

把根因分析（UnionFileSystem 400-1000 倍开销 + 复现基准）整理成 issue 提给
tartaricacid/touhou-little-maid。上游加一个"已存在则跳过"的判断就根治。
- 优点：零维护、惠及所有用户；缺点：等上游、无法控制时间线。可与方案 1 并行。

### 方案 5：fork TLM 直接改源码（不推荐）

把 `copyFolder` 改掉重新发布 jar。效果与 mixin 相同，但要**永远维护一个 TLM 分叉**、
跟着上游版本走。mixin 方案已经用 1% 的成本拿到同样结果，fork 纯亏。

### 已排除的方案（做过功课的）

| 方案 | 排除原因 |
|---|---|
| RAM disk / 换 SSD | 瓶颈是 UnionFileSystem 协议层，不是 IO（基准：同盘 0.96s） |
| Defender 排除（已做） | 收益不稳定（813/471/1113s 三次实测），只是叠加放大器 |
| JVM 参数 / 安全管理器调整 | UnionFileSystem 逐文件开销无对外调节点 |
| `tlm_custom_pack` 只读 | 上游会抛 1260 个异常，行为不可控，且阻止合法更新 |

## 四、结论

**建议升级 tlm_fastpack 到 v1.1 = 方案 1 + 方案 2**：

```
所有场景的默认包处理耗时：8-19 分钟 → 全部 < 3 秒
触发全拷的场景从 4 个减少到 1 个（真正的内容变化）
```

改动范围：`PackState` 增加增量同步与 CRC 清单（~120 行），mixin HEAD 决策改三态，
marker 增加 CRC 清单字段。兼容性面不变（同一个注入点、同样的降级路径），
需要一次重启 + 一次 reset 验证（现在重启只要 ~1.5 分钟，验证成本很低）。
